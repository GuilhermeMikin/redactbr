# RedactBR v0.1 specification

**Status:** pre-alpha draft. This document is the behavior contract for the code on `main`; tests refer to
it. When the code and this document disagree, that is a bug in one of them. Sources were accessed on
2026-10-30 unless stated otherwise.

## 1. Scope

RedactBR finds personal data in text, in-process, and replaces it either with a typed label (`<CPF>`) or
with a reversible session token (`<CPF_k7q2xm9pb3>`) that can be restored later, including in a streamed
LLM response. v0.1 covers CPF, CNPJ (numeric and alphanumeric) and email addresses.

Two principles separate the concerns:

> **Validation determines candidate validity; detection policy determines whether a valid candidate
> should actually be redacted.**

> **Internal failures fail closed; detection uncertainty is a policy decision.** (See §14.)

Validators live in `internal/cpf` and `internal/cnpj` and know nothing about text. Shapes, boundaries,
context and policy live in the root package (`scan.go`, `email.go`).

## 3. Check-digit algorithms

### 3.1 CPF

Eleven digits: nine base digits and two check digits.

- First check digit: multiply the nine base digits by weights 10, 9, …, 2 and sum; let *r* = sum mod 11;
  the digit is 0 if *r* < 2, otherwise 11 − *r*.
- Second check digit: the same over the first ten digits (base plus first check digit) with weights
  11, 10, …, 2.
- `00000000000` is rejected. Other repeated-digit numbers (`11111111111`, …) satisfy the algorithm and are
  **accepted**: the official routine below rejects only the all-zero number, and no official rule about
  repeated digits was found. Redacting a placeholder costs little; missing a real identifier costs more.

**Sources** (read on 2026-11-06). They are of different kinds, and this document keeps them apart:

All three formulations give the same digits. Writing *s* for the sum with the weights above (10 down to 2)
and *t* for the sum with the manual's weights (1 up to 9 from the left), *s* + *t* = 11 · Σ dᵢ, so
*t* ≡ −*s* (mod 11), and the manual's "*t* mod 11, with 10 taken as 0" is "0 if *s* mod 11 < 2, otherwise
11 − *s* mod 11". The same holds for the second digit. `(10·s) mod 11`, in `TestaCPF`, equals
`(11 − s mod 11) mod 11`. Tests port the manual's rule and `TestaCPF` independently and compare them with the
implementation (`internal/cpf`). The manual's text has no exclusion for `00000000000`, whose check digits
it computes as `00`; RedactBR rejects that number, following `TestaCPF`.

### 3.2 CNPJ, numeric and alphanumeric

Fourteen characters: twelve base characters (root of eight, order of four) and two numeric check digits.
In the alphanumeric format the twelve base characters may be digits or the uppercase letters A–Z; the check
digits stay numeric. The numeric CNPJ is the special case where all base characters are digits.

- Each base character is worth its ASCII code minus 48: `0`–`9` → 0–9, `A` → 17, …, `Z` → 42.
- First check digit: weights 5, 4, 3, 2, 9, 8, 7, 6, 5, 4, 3, 2 (2 to 9 from the right, restarting after
  the eighth character); *r* = sum mod 11; 0 if *r* < 2, otherwise 11 − *r*.
- Second check digit: the same over the twelve characters plus the first check digit with weights
  6, 5, 4, 3, 2, 9, 8, 7, 6, 5, 4, 3, 2.
- `00000000000000` is rejected, as in the official reference routines. Lowercase letters are invalid for
  the validator (official reference tests reject `1345c3A5000106`); detection folds case first (§8).
- All 26 letters are accepted. The Receita Federal says some letter combinations will not be issued, that
  the control is internal, and that systems must accept all letters (FAQ questions 38 and 45).

### 3.3 Discrepancy in the official FAQ

FAQ question 23 shows three examples. Examples 2 (`AA345678/000A-29`) and 3 (`12.345.678/000A-08`) satisfy
the published algorithm. Example 1 (`AA345678/0003-29`) does not: the algorithm yields `86` for that base.
RedactBR follows the algorithm, and the test suite keeps example 1 as a negative vector. The FAQ
illustrates formats, so a copy-paste error there is the likely explanation.

## 4. Inputs and outputs

- Input is a Go `string` of any content, including invalid UTF-8. Offsets are byte offsets.
- `Redactor.Find` returns matches sorted by offset, without overlaps. A `Match` carries the entity and
  offsets, never the value.
- `Redactor.Redact` replaces each match with `<` + entity label + `>`. It cannot fail.
- A zero `Redactor` (not created with `New`) behaves like `New()` without options; it never detects
  nothing.
- Bytes outside matches are copied unchanged, including invalid UTF-8.

## 5. Candidate shapes

A candidate must match one of the shapes exactly. Separators are fixed: `.` and `-` for CPF; `.`, `/` and
`-` for CNPJ.

| Shape | Class | Example (generated) |
|---|---|---|
| `DDD.DDD.DDD-DD` | CPF, formatted | `123.456.789-09` |
| `DDDDDDDDD-DD` | CPF, unformatted | `123456789-09` |
| `DDDDDDDDDDD` | CPF, unformatted | `12345678909` |
| `XX.XXX.XXX/XXXX-DD` | CNPJ, formatted | `11.223.344/5566-13`, `AB.12C.D34/EF56-02` |
| `XXXXXXXX/XXXX-DD`, no lowercase letters | CNPJ, formatted | `AB12CD34/EF56-02` |
| `XXXXXXXX/XXXX-DD`, with lowercase letters | CNPJ, unformatted | `ab12cd34/ef56-02` |
| `XXXXXXXXXXXXDD` | CNPJ, unformatted | `11223344556613`, `AB12CD34EF5602` |

Why these classes:

- The CNPJ variant without dots keeps the `/` and `-` that define the CNPJ structure, and the Receita
  Federal's own FAQ uses it (question 23), so it counts as formatted.
- With lowercase letters, that variant looks like a URL path segment (`20261030/main-12`, and about one
  such segment in a hundred has valid check digits), so it counts as unformatted.
- The CPF variant `DDDDDDDDD-DD` is partially formatted. It keeps only a check-digit hyphen, which many other
  identifiers also use (bank accounts, protocols), so it does not earn the confidence of the full mask and
  the policy treats it as unformatted.
- Anything else is **not a candidate**: partial dots (`123.456789-09`), other separators (`123-456-789-09`,
  `123 456 789 09`, `123.456.789/09`), extra digits, letters in check digits.

Nothing is ever detected only because it has the right length: every candidate must also have valid check
digits (§3).

## 6. Boundaries

A candidate is rejected when:

- the rune immediately before or after it is a letter, a digit or a combining mark in any script
  (`x12345678909`, `12345678909x`, `é12345678909`, `123456789091`). The Portuguese ordinal indicators `ª`
  and `º` are letters in Unicode but are boundaries here, so `CPF nº123.456.789-09` is detected; or
- it is immediately preceded by `.` that follows an ASCII digit, or followed by `.` that precedes an ASCII
  digit: the candidate would be part of a decimal or dotted number (`0.12345678909`, `12345678909.5`,
  `1.123.456.789-09`). Exception: a `.` right after a detected value separates two values
  (`12345678909.AB12CD34EF5602` under Strict yields two matches), which also keeps the result stable when
  the first value is replaced.

A value glued to a keyword (`CPF123.456.789-09`, `cpf12345678909`) is therefore not detected.

Exception: the letter of an escape sequence written out as two characters, `\n`, `\r` or `\t`, does not glue
a value to it. JSON strings, logs and source code carry line breaks that way, and tool results often reach
models as JSON, so `"lista:\n123.456.789-09"` contains a candidate. The same text with a real line break does too.

Everything else is a boundary, including whitespace, punctuation, `_`, `-`, `/`, quotes, brackets,
non-breaking spaces and invalid UTF-8. So `cpf_12345678909`, `"12345678909"`, `id-12345678909` and
`/suppliers/11223344556613/orders` contain candidates; whether they are redacted depends on the policy.

A comma is a boundary on purpose: values in CSV rows (`1,12345678909,…`) must stay detectable, at the cost
of not recognizing Brazilian decimal numbers such as `12345678909,50` as numbers.

## 7. Detection policy

Under a uniform distribution, one in a hundred arbitrary 11-digit numbers has valid CPF check digits (each
check digit is a function of the preceding digits, and the last two digits are free), and the same holds
for 14-character CNPJ candidates. Agent and LLM traffic is full of numeric ids, so a checksum match alone
is weak evidence for unformatted values.

| | Formatted, valid | Unformatted, valid, with context | Unformatted, valid, without context | Invalid check digits |
|---|---|---|---|---|
| **Balanced** (default) | redacted | redacted | **kept** | kept |
| **Strict** | redacted | redacted | redacted | kept |

"Formatted" and "unformatted" are the classes in §5. **Context** for an unformatted value is any of the
following, where the keyword is `cpf` for CPF and `cnpj` for CNPJ, matched case-insensitively (ASCII) with
optional dots between its letters. One entity's keyword does not count for the other.

1. **Keyword before.** The keyword, as a substring, lies entirely within the 32 bytes immediately before
   the value's first byte. So `CPF:`, `Cpf`, `C.P.F.`, `customerCpf`, `nr_cpf`, `CPF/CNPJ`, an XML element
   (`<CPF>`) and a label on the previous line all count.
2. **Keyword after.** The keyword lies entirely within the 32 bytes immediately after the value's last
   byte, and all of the following hold:
   - between the value and the keyword there is no digit (another number is closer to the keyword), no line
     break, no backslash (an escape sequence) and no sentence end (`.`, `;`, `!`, `?`);
   - the keyword is a word of its own: no letter, digit, combining mark or `_` on either side, with an
     optional plural `s` (`CPFs`);
   - the keyword does not label what comes next: after any spaces, tabs, quotes, `-`, `(`, `[` or `#`, the next
     character is not `:`, `=` or a digit.
3. **List.** The value follows, within 32 bytes, a value of the same entity that has context, formatted or
   not. And when a value has context from a keyword after it, the earlier values of the same entity get that
   context too, as long as each is within 32 bytes of the next.

The rule after the value is stricter because labels precede values in nearly every format (`CPF: …`,
`"cpf": …`, `cpf=…`). A keyword before a value is good evidence; a keyword after a value is often the label
of the next field. A symmetric window would make the `id` below a CPF one time in a hundred.

| Text (generated values) | Balanced | Why |
|---|---|---|
| `CPF: 12345678909` | `CPF: <CPF>` | keyword before |
| `12345678909 é meu CPF` | `<CPF> é meu CPF` | keyword after |
| `12345678909 (CPF)` | `<CPF> (CPF)` | keyword after |
| `{"doc":"12345678909","tipo":"CPF"}` | `{"doc":"<CPF>","tipo":"CPF"}` | keyword after, as the next field's value |
| `id=12345678909 cpf=98765432100` | `id=12345678909 cpf=<CPF>` | `cpf=` labels what follows it |
| `{"id":"12345678909","cpf":"98765432100"}` | `{"id":"12345678909","cpf":"<CPF>"}` | `"cpf":` labels what follows it |
| `pedido 12345678909, cpf 98765432100` | `pedido 12345678909, cpf <CPF>` | a number follows the keyword |
| `pedido 12345678909. CPF do cliente` | unchanged | another sentence |
| `pedido 12345678909` + line break + `CPF do cliente` | unchanged | another line |
| `12345678909 customerCpf` | unchanged | not a word of its own |
| `CPFs: 12345678909, 98765432100, 31415926590, 12345678909` | `CPFs: <CPF>, <CPF>, <CPF>, <CPF>` | list, past the 32-byte window |
| `12345678909 e 98765432100 são meus CPFs` | `<CPF> e <CPF> são meus CPFs` | keyword after, shared by the list |
| `order 12345678909 shipped` | unchanged | no context |

- **Trade-off:** Balanced misses unformatted values without context — values alone on a line, CSV columns
  whose header is far away, URL paths. Strict catches them and also redacts ids, timestamps and codes that
  happen to have valid check digits. Neither policy touches values with invalid check digits, so a mistyped
  CPF is not redacted.
- **Residual false positives under Balanced:** context is evidence, not proof. A number with valid check
  digits (one in a hundred) near a keyword that is about something else is redacted (`pedido 12345678909 do
  cliente sem CPF`, `CPF: 123.456.789-09, pedido 98765432100`). Redacting it costs one id in a hundred of
  those that sit next to the word "CPF", which is what the default accepts in exchange for not leaking the
  value when it is a CPF.
- **Already redacted text:** tokens and typed labels contain the keyword, so a second pass over redacted
  text can redact more than the first (a number with valid check digits next to `<CPF>` or `<CPF_…>`). This
  errs towards redaction and cannot undo a replacement.
- **Why not "when in doubt, redact everything":** false positives corrupt LLM prompts and answers
  (order numbers, amounts, ids). The default favors correctness of the surrounding text and requires a
  signal for bare numbers; callers who prefer recall choose Strict.
- **Ambiguity in later versions:** several Brazilian identifiers share lengths (v0.2 adds more). The
  principle stays: each validator decides validity; the policy decides, using shape and context, which
  valid candidates to redact and as which entity.

## 8. Normalization

| Input | v0.1 behavior |
|---|---|
| Separators `.` `-` `/` | Removed for validation and session keys; only the shapes in §5 are recognized |
| Regular spaces inside a value | **Unsupported** (`123 456 789 09` is not detected) |
| Non-breaking space (U+00A0) around a value | Supported as a boundary (`CPF: 12345678909`) |
| Full-width digits (U+FF10–U+FF19) | **Unsupported**: not folded to ASCII, and they block boundaries |
| Invisible characters inside a value (U+200B, U+2060, …) | **Unsupported**: a zero-width space inside a value prevents detection |
| Letter case in CNPJ | Folded to uppercase before validation, in every shape (§8.1) |
| Unicode lookalike separators (en dash, fraction slash) | **Unsupported** |
| Percent-encoded separators (`cpf%3D12345678909`) | **Unsupported**: the hex digits glue to the value |
| Other escapes (`\u00a012345678909`, `11.223.344\/5566-13`) | **Unsupported**: planned with JSON-aware redaction |
| Numbers written out in words | Out of scope |

Unsupported forms are false negatives. Folding them is **planned for evaluation** (an opt-in
normalization step), not done silently: every fold widens what counts as a candidate, and folding
invisible characters changes offsets.

### 8.1 Lowercase alphanumeric CNPJ

The official format uses uppercase letters, and the official validator rejects lowercase. People type
lowercase, though, and a lowercase CNPJ identifies the same company. Detection therefore folds case before
validation, in every shape. Under Strict this adds 14-character lowercase codes ending in two digits to the
false-positive surface (about 1 in 100 of them). This is a deliberate deviation from the official format,
limited to detection. The variant without dots counts as formatted only when it has no lowercase letters
(§5).

## 9. Overlaps

Identifier matches never overlap by construction. Email and identifier matches can (`12345678909@x.com`).
Overlaps are resolved by keeping the match that starts first; between matches that start at the same
offset, the longest wins.

## 10. Email

A pragmatic subset of the RFC 5322 `addr-spec` (§3.4.1: `local-part "@" domain`, with `dot-atom`
local parts and domains, §3.2.3), with the RFC 5321 limits (§4.5.3.1.1: local part at most 64 octets;
§4.5.3.1.2: domain at most 255 octets):

- **Local part:** ASCII letters, digits and `._%+-'`, plus letters, digits and combining marks of other
  scripts, so that `sant'anna@…` and addresses with accented letters (composed or decomposed) are
  redacted whole. Leading dots and apostrophes are punctuation (`'ana@example.com'`), and a local part starts
  after an escape sequence written out as two characters (§6), so `\nana@example.com` keeps its `\n`. Longer
  than 64 bytes after that: not detected. Other RFC 5322 `atext` characters (`/`, `=`, `?`, …) are excluded because they
  would pull URL text into the match.
- **Domain:** at least two labels of letters, digits and hyphens (RFC 5321 §4.1.2 `sub-domain`), no empty
  label, no label starting or ending with `-`. The last label has at least two letters, or starts with
  `xn--` in any case. Text glued after the domain is left out: the longest prefix that ends before a `.`
  or `-` and forms a valid domain is used (`ana@example.com-thanks`, `ana@example.com.2`, trailing dots).
  Longer than 255 bytes: only a valid prefix within the limit is used.
- **Not recognized:** quoted local parts, comments, IP address literals (`user@[192.0.2.1]`), single-label
  domains (`user@localhost`), numeric top-level labels.
- A local part never extends back into the previous address (`a@b.co@c.co` yields one match).
- No context is required under either policy.

## 11. Typed replacement

`Redactor.Redact` replaces each match with `<CPF>`, `<CNPJ>` or `<EMAIL>`. The replacement is irreversible
and the same for every value of an entity. Each replacement grows the text by at most one byte (an email
can be as short as six bytes; `<EMAIL>` has seven).

### 11.1 Log records

`Redactor.NewSlogHandler(next)` returns a `log/slog` handler that applies typed replacement to each record and
passes the result to `next`. The original record is not modified. Logs are not restored, so it uses no session.

- **Messages, attribute keys and group names** are redacted as text.
- **The name of a field is context for its value.** A value is judged as if it followed `name=`, where the name
  includes its groups, so `slog.String("cpf", "12345678909")` and `slog.Group("cpf", "numero", "12345678909")`
  are redacted under Balanced, and `slog.String("id", "12345678909")` is not. Only the field's own name counts:
  the message and other attributes are not context, so `slog.String("tipo", "cpf"), slog.String("doc",
  "12345678909")` is kept under Balanced.
- **Numbers are checked too**: `slog.Int64("cpf", 12345678909)` is logged as the string `<CPF>`. A number without
  a match stays a number. So do booleans, durations and times.
- **Any other value** (errors, `Stringer`s, structs, maps, slices) is logged as a string: its `%+v` text, redacted,
  or for `[]byte` the bytes as text. The handler cannot see inside an arbitrary value, and a JSON handler would
  otherwise marshal fields, such as those behind pointers, that the text form does not show. The cost is that
  structured values lose their structure in the log. A nil value stays nil.
- **`LogValuer`s are resolved** before any of this, and groups are handled attribute by attribute.
- Nothing is logged in the clear on failure. The handler has no failure of its own: a value whose `String`
  method panics is logged with the panic text `fmt` writes, redacted, and an error from `next` is returned.

## 12. Reversible sessions

### 12.1 Token grammar

```abnf
token   = "<" entity "_" id ">"
entity  = "CPF" / "CNPJ" / "EMAIL"
id      = 10idchar
idchar  = DIGIT / %x61-68 / %x6A-6B / %x6D-6E / %x70-74 / %x76-7A
          ; lowercase Crockford base32: 0-9 a-z without i, l, o, u
```

- Maximum token length: 18 bytes (`<EMAIL_` + 10 + `>`).
- The id is 10 symbols × 5 bits = **50 bits** from `crypto/rand`, drawn for every new value. Tokens carry
  no counter, no session tag and no information about the value. Random bytes are reduced with `b & 31`;
  256 is a multiple of 32, so the symbols are uniform.
- Tokens are matched **byte for byte**. Any change — case, spacing, length, separator, entity — makes text
  not a token of the session.

### 12.2 Issuance

- `Session.Redact` detects values with the Redactor's settings (§5–§10) and replaces each with its token.
- Equal values share a token for the lifetime of the session. Equality uses the normalized form: CPF and
  CNPJ without separators and in uppercase; email with the domain lowercased (the local part is
  case-sensitive), so `123.456.789-09` and `12345678909` share a token, and `ana@x.com` and `Ana@x.com` do
  not.
- `Session.Restore` returns the value **as first seen** by the session.
- An id is drawn at most 8 times per new value; if every draw collides with an issued or reserved token,
  the call fails (§14).

### 12.3 Pre-existing token-like text

> Pre-existing token-like text in user input must never gain restoration authority merely because the
> session later emitted an identical-looking token.

Before issuing tokens, `Session.Redact` collects every well-formed token in its input that the session
has not issued and **reserves** it: the session will never issue a reserved string. Reservation happens
before issuance within the same call, so a look-alike and a real value in the same input cannot collide.
Tokens the session did issue (conversation history sent again) are left alone and stay restorable.

The guarantee covers text that passes through `Session.Redact`. Text that reaches the model by another
path (a system prompt added later, tool output) is not seen by the session; the 50-bit random id makes a
collision with it improbable (about *n*/2⁵⁰ per look-alike for *n* tokens of that entity), not
impossible. Route all model-bound text through the session.

Covered by `TestPreexistingTokenLiteralNeverGainsAuthority` (the random source is forced to draw the
look-alike's id), `TestRestoreLeavesEverythingElseVerbatim` (`<CPF_1>`, `<CPF_01>`, `<CPF_1 >`, `<cpf_1>`,
`<RANDOMTHING>`, modified tokens) and `FuzzSessionRoundTrip`, whose random source cycles through four ids
so that collisions with look-alikes in the input are frequent. Removing the reservation makes both fail.

### 12.4 Restoration

- `Session.Restore` and `RestoreWriter` replace only tokens present in the session's issued set.
- Unknown, forged, modified, reserved and foreign (other sessions') tokens are left **verbatim**; nothing
  is removed or reported. A model that mangles a token therefore shows the mangled token, never a value.
- Restoration does not re-scan restored values; values cannot form tokens (they contain no `<`).
- A session never restores another session's tokens: each session restores from its own issued set only.

### 12.5 Capacity

- A session holds at most `WithMaxSessionValues(n)` entries (default 10,000), counting distinct values
  and reserved strings. A call that would exceed it returns `ErrSessionFull`.
- Someone who controls a session's input can fill it with token-like strings; the session then fails
  closed. Sessions are per conversation, so this affects only the session that received the input.
- Stored values and reservations are copies, not substrings of the input, so a session does not keep its
  inputs (or undetected data in them) alive. Its memory grows with the number and size of distinct values.

### 12.6 Concurrency

`Session` is safe for concurrent use: `Redact` takes a write lock for its whole state transition;
`Restore` and `RestoreWriter.Write` take a read lock while they look tokens up. Concurrent calls that see
the same new value agree on one token (`TestSessionConcurrentUse`, run with `-race` in CI).

### 12.7 Formatting

`Session` and `RestoreWriter` implement `String` and `GoString` with counts only, so `%v`, `%+v` and `%#v`
do not print values, tokens or buffered text, including when the variable is dereferenced or sits inside
another struct: a `Session` holds its state behind a pointer, and `RestoreWriter` formats by value.
`encoding/json` sees no exported fields in either.

### 12.8 Accidents and adversaries

Two kinds of problem get mixed up when talking about tokens. The mechanism is strong against the first kind,
accidents. It makes no promise about the second kind where it matters most: someone repeating a valid token
on purpose.

| Situation | Cause | What stops it | Strength |
|---|---|---|---|
| Two values drawing the same id | Chance | A collision with an issued or reserved token is drawn again, up to 8 draws, then the call fails | Deterministic: a token never stands for two values |
| A look-alike in text that passed through `Session.Redact` | A user quoting something | Reservation (§12.3) | Deterministic |
| A look-alike that did not pass through the session whole (a system prompt, a document, text split across calls) | Chance | The 50-bit id | Probabilistic: about *n*/2⁵⁰ per look-alike |
| A model mangling a token (case, spacing, brackets, a character) | Model error | Byte-for-byte matching | Deterministic against restoring a wrong value; the reader sees the broken token. How often it happens is what [the fidelity harness](../token-fidelity.md) measures |
| A token from another session | An application mixing sessions up | Each session restores from its own issued set | Deterministic, unless the same id was issued there too (about *n*/2⁵⁰) |
| A model putting a valid token in the wrong place (swapping two customers) | Model error | **Nothing** | Not detected: restoration is faithful to the token, not to what the sentence means |
| Guessing a token never seen | A malicious user or model | The 50-bit id | About *n*/2⁵⁰ per guess; 9 × 10⁻¹² for a full session of 10,000 tokens of one entity |
| Filling a session with look-alikes | Whoever controls its input | The capacity (§12.5) | The session fails closed; only its availability is at stake |
| **Repeating a valid token**, by a user who saw it or a model told to | A malicious user, prompt injection | **Nothing** | **Not protected.** A token is a bearer reference, not an authorization: whoever gets a text with it restored by the session gets the value |
| **Steering a restored value somewhere else** (a link or image URL in Markdown, a tool-call argument) | Prompt injection | **Nothing** | **Not protected.** Restoration replaces text and does not know where the token is |

`TestValidTokenRestoresWhoeverWritesIt` and `TestReservationLimits` pin the limits down, so that they are not
mistaken for bugs or guarantees. Numbers: with *n* tokens of an entity, a guess succeeds with probability
*n*/2⁵⁰. A collision among 10,000 new ids has probability about *n*²/2⁵¹ ≈ 4 × 10⁻⁸, and it only causes one
more draw.

What this means for callers:

- **Restore only what the reader of the output may see.** A session restores everything it tokenized. A tool
  result with data the current reader must not see does not belong in the session that is restored for that
  reader: use `Redactor.Redact`, which is irreversible, or a separate session that is never restored.
- **Restored text is model output with real values in it.** Restore as the last step, and do not hand the
  result to something that follows links, loads images or runs tools without the checks that output would
  need anyway. Restored values are raw text (an email local part can contain `'`), so escape them for their
  destination (HTML, SQL, shell).
- **Tokens reveal the entity and equality within a session.** The provider can see that a value is a CPF and
  that two mentions are the same value. That keeps prompts stable; tokens reveal nothing else about the value.

## 13. Streaming restoration

`Session.RestoreWriter(w)` returns an `io.Writer` that restores tokens and writes to `w`.

- A token split across any number of writes is restored, provided it is complete before `Close`.
- Between writes the writer holds back only a trailing fragment that could still become a token: at most
  17 bytes (one token minus one byte). Any other byte is written in the same `Write` call. Long
  attacker-controlled prefixes (`<CPF_` followed by thousands of id characters, runs of `<`) do not grow
  the buffer (`TestRestoreWriterBoundsHeldBytes`).
- `Close` writes held-back bytes; an unfinished token at the end of the stream is written as it is.
  `Close` does not close `w`. A second `Close` returns nil; `Write` after `Close` returns an error.
- If `w` fails, the error is returned and is sticky for every later call. Nothing is retried.
- A `RestoreWriter` is not safe for concurrent use; use one per stream. Tokens issued after the writer was
  created are restored too.
- Feed it **decoded text** — the model's text deltas — not a raw SSE or JSON body: a token split across
  events has framing between its halves, and JSON encoders may escape `<` and `>` (Go's `encoding/json`
  writes `\u003c` and `\u003e` by default), which hides the token.
- Tests split a stream at every offset and in 1-byte chunks and compare with `Session.Restore`; a fuzz
  target does the same with arbitrary chunk sizes.

## 14. Failure semantics

**A — Internal failures fail closed.** When a caller asks for redaction and the operation cannot complete,
the API returns an error and **an empty result, never the original input**:

- `New` rejects invalid configuration, including an empty entity list (a redactor that detects nothing
  would pass everything through). A zero `Redactor` detects everything.
- `Session.Redact` returns `("", err)` on `ErrSessionFull`, on a random-source error, or when no unused id
  can be drawn; the session is left unchanged (all checks happen before any state is modified).
- `Redactor.Redact` has no failure mode: it works on an in-memory string.
- The package never `recover()`s a panic to return unredacted text.

**B — Detection uncertainty is a policy, not a failure.** Not knowing whether `12345678909` is a CPF is
not an error; the policy (§7) decides. "Redact everything when in doubt" is available as Strict, not
imposed.

## 15. Personal data in errors and logs

- Errors name the package, a category and, where useful, a count; never a value or a token. Configuration
  errors may echo the configuration value (an unknown entity name), which is not personal data.
- `Match.String()` prints `ENTITY[start:end]`. `Session` and `RestoreWriter` format as counts (§12.7).
- The package does not log, except through a handler the caller installs (§11.1). Benchmark and test names
  contain no values. Tests use only generated
  fixtures and official reference vectors, so their failure messages may print those.

## 16. Threat model

RedactBR is a **data-minimization control** for well-intentioned applications. It helps against:

1. accidental disclosure of personal data to LLM providers and other third-party APIs;
2. accidental disclosure in logs, traces and analytics;
3. LLM answers that need to reuse values the user provided, without the provider seeing them.

It does **not** promise protection against:

- a malicious user who wants to exfiltrate data on purpose (spacing out digits, writing them in words,
  inserting invisible characters, encoding them);
- personal data in images, PDFs, audio or OCR output that has not been turned into text;
- names, addresses and other free-form personal data (no NER in v0.1);
- prompt injection in general, or a user or model repeating a valid token: a model told to repeat every
  token it saw will do so, and restoration will reveal those values to whoever receives the restored text, or
  to wherever that text sends them (§12.8) — restoration is an authorization decision;
- a compromised process, memory inspection, core dumps, swap or side channels: values are ordinary Go
  strings in memory and cannot be reliably wiped;
- identifiers outside §2, or forms outside §5 and §8.

Session-specific assumptions: a session is a trust scope; everything it tokenized can be restored into any
text given to it. Tokens are unguessable (50 bits) but not secret: anyone who sees a token and can get text
restored by the same session can learn the value. Use one session per conversation, never one shared
across users or tenants. §12.8 separates what is protected from what is not.

Compliance: the library supports privacy programs such as LGPD data minimization; using it does not make a
system compliant.

## 17. Fixtures

Fixtures are **generated, never collected**. A generated identifier with valid check digits can still
coincide with one that was assigned to someone, so the rule is "generated, never collected", not
"guaranteed to belong to nobody". Fixture sets stay small and explainable (sequential digits, repeated
pairs, letter patterns). Validator tests also use the vectors that the Receita Federal publishes in its
reference routines and FAQ, cited where they are used; CNPJ numbers are public registry data.

## 18. Limits and complexity

- `Find`/`Redact`: linear in the input — one pass for email, one for identifiers and, when both find
  something or a keyword reaches back over a list, a sort of the matches. Identifier candidates are at most 18
  bytes, context looks at no more than 32 bytes around a candidate, the domain scan after each `@` is bounded
  (256 bytes), and local-part walks never revisit bytes. The bound on the domain scan has a cost in the worst
  case, addresses followed by long dotted domains that never validate (`BenchmarkRedactEmailWorstCase`), which
  runs tens to hundreds of times slower per byte than ordinary text and is still linear.
- `Session.Redact`: linear in the input plus map operations per match; memory grows with distinct values
  up to the capacity.
- `RestoreWriter`: linear in the bytes written; at most 17 bytes held between writes.

## 19. Open questions

- CPF check digits: normative definition (pending official source; see §3.1). The algorithm itself is
  documented by the Receita Federal; the text of IN RFB 2.172/2024 has not been read.
- Should partially punctuated forms (`123.456789-09`) or spaced forms become candidates under Strict?
- Should the context window (32 bytes) be configurable? Nothing so far shows that callers need it, and a
  knob would widen what has to be tested.
- Opt-in normalization of full-width digits and invisible characters (§8).
